    Learn TRACII

    What is TRACII?How it worksKey terms Reading your reportLimitations

    What is TRACII?

    TRACII is an AI-powered application and software supply-chain security platform that investigates software dependencies, detects vulnerabilities and suspicious behaviour, traces their impact on your application, and recommends evidence-backed fixes.

    Today it analyses npm projects (package.json + package-lock.json).

    How TRACII works

    1. ScanConnect a public GitHub repository, upload package.json + package-lock.json, or try a demo project.
    2. DetectIdentify known vulnerabilities, known malicious packages and suspicious code behaviour, without installing or running any package.
    3. TraceMap direct and transitive dependencies and see the path each risk takes into your application.
    4. InvestigateUse Meta AI models and investigation agents to explain findings, analyse the evidence and assess potential impact.
    5. Fix & VerifyGet a proposed dependency change, simulate it in an isolated sandbox and rescan to verify it worked. You decide whether to apply it; TRACII never modifies your repository.

    Key terms, in plain words

    Open a group to read it. Each term is one or two sentences.

    The basics: what is being checked
    Dependency / package
    A ready-made piece of code your app borrows instead of writing it, like a part a car maker buys from a supplier.
    npm
    The public store where JavaScript packages are published and downloaded. TRACII checks npm projects.
    package.json
    Your app's shopping list: the packages you asked for.
    Lockfile (package-lock.json)
    The receipt: the exact version of every package that actually got installed, including the ones you never asked for directly.
    Direct dependency
    A package your app asks for by name.
    Transitive dependency
    A package that comes along because another package needs it: the supplier's supplier.
    Dev-only dependency
    A package used only while building or testing, not shipped to your users. Problems there matter less.
    Install script
    A small program a package can run automatically when it is installed. Useful for setup, but also the most common way malware gets in.
    Version
    A numbered release of a package, like 4.17.20. A change in the first number (a “major version”) can break things.
    What TRACII can find
    Vulnerability
    A known security bug in a package version, like a recall notice for a faulty part.
    Malware
    Code written on purpose to do harm, such as stealing passwords or keys.
    Known malware
    A package version already reported as malicious in a public list. The strongest kind of finding: remove it.
    Suspicious code
    Package code that behaves like malware often does (for example, sending your data somewhere when installed). A warning to review, not proof.
    Severity
    How serious a finding is: Critical, High, Medium, Low. “Info” is just context, not a problem.
    Evidence
    The facts behind a finding, such as the advisory text or the exact line of code, with a link to check it yourself.
    Impact path
    The chain of packages that brings a risky one into your app, for example your app → express → qs.
    Confidence
    How sure the scanner is. High means an exact match to a published report; low means a single hint that is often harmless.
    False positive
    A warning that turns out not to be a real problem.
    Repository posture
    General security hygiene of the project's code repository. Not enabled in scans yet; it is shown as skipped.
    Licence
    The legal terms for using a package. Some (“copyleft”) come with obligations; TRACII lists them, it does not give legal advice.
    Where the information comes from
    OSV
    A free, public database run by Google that collects security reports for open-source packages. TRACII asks it about every exact version you install.
    Advisory (CVE, GHSA)
    A published security report about a package. CVE-… and GHSA-… are their ID numbers, like a case number.
    MAL- record
    An OSV report saying a package version is malware. This is TRACII's “known malware list”. A package that is not on it is not automatically safe.
    GuardDog
    A free tool from the security company Datadog that reads package code and flags patterns typical of malware, such as hidden downloads or stealing environment data.
    TRACII behaviour rules
    TRACII's own checks that read package code for attack patterns (for example “collect secrets, then send them over the internet”). Code is only read, never run.
    Version diff
    A side-by-side comparison of two releases of one package, to spot a new install script or hidden code that was slipped in.
    Evaluation / benchmark
    Testing TRACII's detectors on packages already known to be good or bad, to measure how much they catch and how often they raise false alarms.
    Fixing and reporting
    Remediation / fix
    The change that removes the risk, usually upgrading to a version where the bug is fixed.
    Fix plan
    TRACII's short to-do list: remove known malware first, then the few upgrades that fix the most vulnerabilities.
    Override
    A line in package.json that forces a safer version of a package you do not use directly.
    Simulate and rescan
    TRACII tries the fix in a sealed test area (sandbox) and scans again, so you see it works before changing anything. Your project is never modified.
    CI/CD
    The automatic checks that run every time code changes, before it is released.
    CI security gate
    A checkpoint in those automatic checks. PASS lets the release continue; FAIL stops it when a problem is at or above the chosen severity.
    SBOM
    “Software Bill of Materials”: a full ingredients list of your app's packages. CycloneDX is the standard file format for it.
    SARIF
    A standard file format for scan results, so tools like GitHub can show them.
    SCA
    “Software Composition Analysis”: checking the third-party parts of your app for security and licence risks. That is what TRACII does.
    Views and AI
    Impact map
    A simple tree showing only the paths that lead to problems, from your app down to the risky package.
    3D graph
    Every package in your project as a dot you can rotate and click. Colour shows what was found; bigger dots are used by more packages.
    Attack replay
    A step-by-step re-enactment of a real past attack (such as event-stream in 2018) on your own graph, to show what it would reach. Clearly marked as a simulation when your project does not use that package.
    Meta Muse models
    The AI models TRACII uses to explain findings in plain language and answer questions. They only see the scanner's evidence.
    AI agents
    Several AI “specialists” that each look at a finding with a recognised method (how likely an attack is, what an attacker would do, how trustworthy the package's build is, what could go wrong), plus a judge that combines them.
    Second opinion
    Another AI model (Muse Spark Open or Muse Glimmer) that reviews the same evidence independently, so you can see whether they agree.

    Reading your results

    • Overview. One headline (is anything serious?), three counts (known malware, vulnerabilities, suspicious code) and a fix plan: what to remove or upgrade first. Click any count or step to see the details.
    • Findings. One row per package, not per report. “lodash 4.17.20 · 5 vulnerabilities · upgrade to 4.18.0 fixes all” tells you the whole story; open it to see each issue in plain words. Tabs only appear when they have something in them.
    • Severity. Critical and High first; Medium and Low are real but less urgent; Info notes (such as “has an install script”) are hidden unless you ask for them.
    • Impact map. How each risky package reaches your app. “Explore in 3D” shows the whole project as an interactive graph; attack replays live there too.
    • Evidence and AI. Each finding shows its evidence with a source link. “Explain with AI” turns that evidence into plain language; the AI must point to the evidence for every claim and can never change the scanner's verdict.
    • Fixing. “Propose fix” shows the exact change; “Simulate fix and rescan” proves it in a sandbox. A finding counts as fixed only after that rescan.
    • CI gate & reports. PASS or FAIL at the severity you choose (default: High), plus downloads: PDF report, SBOM, SARIF and a gate summary.
    • Scan details. Which checks ran and which did not, and the licences of your packages.
    • Ask AI. Ask a question about this scan in plain words, typed or spoken; answers point to the findings they are based on.
    • Your last scan is kept in this browser, so you can reopen it from New scan later.

    Important limitations

    • No detected issue does not guarantee that an application is completely secure.
    • Suspicious behaviour indicators are not automatically confirmed malware.
    • An advisory match does not necessarily prove that vulnerable code is reachable or exploited.
    • AI assessments explain scanner evidence; they never override the deterministic scanner verdict.
    • Offline benchmark evaluation results are separate from your live scan results.
    • A skipped or unexecuted check is never presented as a successful check; the report lists it as not run.
