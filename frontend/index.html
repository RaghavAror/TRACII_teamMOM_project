    Learn TRACII

    What is TRACII?How it worksKey terms Reading your reportLimitations

    What is TRACII?

    TRACII is an AI-powered application and software supply-chain security platform that investigates software dependencies, detects vulnerabilities and suspicious behaviour, traces their impact on your application, and recommends evidence-backed fixes.

    Today it analyses npm projects (package.json + package-lock.json).

    How TRACII works

    1. ScanConnect a public GitHub repository, upload package.json + package-lock.json, or try a demo project.
    2. DetectIdentify known vulnerabilities, known malicious packages and suspicious code behaviour, without installing or running any package.
    3. TraceMap direct and transitive dependencies and see the path each risk takes into your application.
    4. InvestigateUse Meta AI models and investigation agents to explain findings, analyse the evidence and assess potential impact.
    5. Fix & VerifyGet a proposed dependency change, simulate it in an isolated sandbox and rescan to verify it worked. You decide whether to apply it; TRACII never modifies your repository.

    Key terminology

    Dependency
    An external software package that an application uses.
    Direct dependency
    A package explicitly included by your application.
    Transitive dependency
    A package brought in through another dependency.
    Vulnerability
    A security weakness that could potentially be exploited.
    Malware
    Software designed to perform harmful or unauthorised actions.
    SCA (Software Composition Analysis)
    Analysing third-party software components for security and licence risks.
    SBOM (Software Bill of Materials)
    A structured inventory of the software components and dependencies used by an application.
    CycloneDX
    A standard format for representing and exchanging an SBOM.
    SARIF
    A standard format for sharing static-analysis and security scan results.
    CI/CD
    Automated workflows that build, test and deliver software.
    CI Security Gate
    A policy-based checkpoint that can fail a build when configured security thresholds are exceeded.
    Severity
    The seriousness of a security finding, commonly Critical, High, Medium or Low.
    Evidence
    Verifiable information supporting a security finding, such as an advisory or code indicator.
    Impact path
    The dependency chain through which a package reaches your application.
    Remediation
    A recommended action to reduce or resolve a security risk.
    False positive
    A reported issue that is not actually a security problem.
    Evaluation / Benchmark
    Testing the detection engine against a separate labelled dataset to measure detection performance and false alarms.
    Known malware list
    A collection of previously identified malicious packages; a package absent from the list is not necessarily safe.
    Version diff
    A comparison of security-relevant changes between two versions of a package.
    Repository posture
    Security-related observations about the repository and its configuration. (Not yet enabled in scans; the report shows this check as skipped.)

    Understanding your scan report

    • Verdict and “look at these first”. The banner states the CI gate result and lists the findings to handle first, ordered by scanner facts only.
    • Findings by type. Four separate counts that are never merged into one score: known vulnerabilities (advisories), known malicious packages (OSV MAL- records), suspicious behaviour (heuristic signals from TRACII rules and GuardDog) and repository posture.
    • Severity. Critical and High deserve attention first; Medium and Low are real but less urgent; Info is context only (for example “has an install script”).
    • Dependency graph. Each dot is a package and each line means “depends on”. Colour shows what the scanners found (yellow = known malware, purple = suspicious behaviour, red/amber/blue = vulnerability severity) and size shows how many packages depend on it. Click a dot to highlight its path up to your app.
    • Evidence. Every finding lists its evidence (advisory text, code location, metadata) with a link to the source: OSV.dev, GitHub advisories, the npm registry or the rule that fired.
    • AI investigation. Meta Muse models explain the scanner's evidence. Every claim must cite an evidence ID or it is discarded, and the AI never changes the scanner's verdict.
    • Remediation and rescanning. “Propose fix” shows the exact package.json change; “Simulate fix and rescan” checks in a sandbox whether the finding disappears. A finding counts as fixed only after that rescan.
    • CI Gate PASS / FAIL. The build is blocked when a finding is at or above the chosen threshold (default: High), or marked incomplete when a required check could not run.
    • Exports. SBOM (CycloneDX) lists every component; SARIF loads into GitHub code scanning; the gate report and PDF report summarise the scan.

    Important limitations

    • No detected issue does not guarantee that an application is completely secure.
    • Suspicious behaviour indicators are not automatically confirmed malware.
    • An advisory match does not necessarily prove that vulnerable code is reachable or exploited.
    • AI assessments explain scanner evidence; they never override the deterministic scanner verdict.
    • Offline benchmark evaluation results are separate from your live scan results.
    • A skipped or unexecuted check is never presented as a successful check; the report lists it as not run.
